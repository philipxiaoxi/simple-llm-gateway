# Requirements Document

## Introduction

正式服已有 4000 余条请求记录，单条记录可达数千条对话消息。现有「记录审计」只能按账号、Key、协议、状态筛选请求元数据，管理员无法在可承受的人工成本下完成合规审阅。

本功能在转发路径之外，对已入库的请求正文和消息做事后扫描，产出「命中项」清单。管理员从独立页面查看命中项，再钻取到原会话上下文。扫描由 24 小时循环任务驱动，并支持在定时任务页手动执行。

第一版覆盖三类检测：敏感词（内置完整开源词库）、PII、密钥。不拦截、不改写上下游流量。

## Glossary

- **请求记录**：`request_logs` 中的一条网关转发记录，对应一次下游调用。
- **消息**：`request_log_messages` 中属于某条请求记录的一条对话消息。
- **命中项**：一次扫描在某条消息（或请求级正文）上发现的一条合规线索，含类别、规则名、摘录和定位信息。
- **内容审计任务**：系统内名为 `content_audit` 的循环定时任务，默认间隔 86400 秒。
- **增量扫描**：只处理尚未扫描、或自上次成功扫描后有更新的请求记录。
- **敏感词库**：运行时从 konsheng/Sensitive-lexicon 下载并缓存的完整开源中文敏感词表，按原库分类保留。
- **PII**：个人身份信息，第一版限定为大陆手机号、18 位身份证号、电子邮箱、银行卡号。
- **密钥**：高置信凭据形态，包括常见 LLM API Key 前缀、Bearer token、PEM 私钥头、GitHub PAT、AWS Access Key ID。

## Requirements

### Requirement 1: 独立命中清单页面

**User Story:** AS 管理员, I want 一个独立于记录审计的命中清单页面, so that 我只处理机器筛出的线索，不必翻 4000 条会话全文。

#### Acceptance Criteria

1. WHEN 管理员打开管理端导航, THE 系统 SHALL 提供独立入口「内容审计」，路径与「记录审计」分离。
2. WHEN 管理员进入内容审计页, THE 系统 SHALL 以命中项列表为默认视图，每行展示时间、类别、规则名、摘录、所属 Key、所属请求记录标识、严重级别。
3. WHEN 命中项列表存在筛选条件, THE 系统 SHALL 支持按类别（敏感词 / PII / 密钥）、敏感词分类、严重级别、时间范围、API Key 过滤。
4. WHEN 管理员点击一条命中项, THE 系统 SHALL 打开对应请求记录详情，并定位到命中消息、高亮命中片段。
5. WHEN 命中项列表为空, THE 系统 SHALL 展示空状态，说明尚无命中或筛选无结果。
6. WHILE 管理员使用移动端, THE 系统 SHALL 以卡片列表展示命中项，并保持与 PC 端相同的筛选能力。

### Requirement 2: 独立管理 API

**User Story:** AS 系统, I want 命中项使用独立的管理路由, so that 内容审计查询与现有记录审计接口解耦，列表查询不必加载整段对话。

#### Acceptance Criteria

1. WHEN 管理员查询命中项, THE 系统 SHALL 通过独立于 `/api/admin/logs` 的管理路由返回分页命中项。
2. WHEN 命中项列表接口返回数据, THE 系统 SHALL 包含命中项标识、请求记录标识、消息序号、类别、规则名、摘录、严重级别、创建时间，以及 Key 名称与账号名称快照。
3. WHEN 管理员请求命中项分页, THE 系统 SHALL 支持页码与页大小，单页上限 100 条。
4. WHEN 管理员携带筛选参数查询, THE 系统 SHALL 仅返回同时满足全部已给条件的命中项。
5. WHEN 未认证或非管理员访问该路由, THE 系统 SHALL 返回与其它管理接口一致的未授权响应。

### Requirement 3: 事后扫描范围与检测类型

**User Story:** AS 管理员, I want 系统扫描已入库对话中的敏感词、PII 和密钥, so that 合规线索被完整列出，转发路径保持不变。

#### Acceptance Criteria

1. WHEN 内容审计任务执行, THE 系统 SHALL 扫描目标请求记录的消息正文；若请求级仍保留可读正文，系统同时扫描该正文。
2. WHEN 扫描进行中, THE 系统 SHALL 继续按原路径转发下游请求，扫描结果只写入命中项存储。
3. WHEN 文本匹配敏感词库中的词条, THE 系统 SHALL 生成类别为「敏感词」的命中项，并记录词条所属分类与词条原文。
4. WHEN 文本匹配 PII 规则（大陆手机号、18 位身份证号、电子邮箱、通过 Luhn 校验的银行卡号）, THE 系统 SHALL 生成类别为「PII」的命中项，并记录具体规则名。
5. WHEN 文本匹配密钥规则（`sk-` / `sk-ant-` 等 LLM Key 形态、Bearer 长 token、PEM 私钥头、`ghp_`、`AKIA`）, THE 系统 SHALL 生成类别为「密钥」的命中项，并记录具体规则名。
6. WHEN 同一条消息被同一规则命中多次, THE 系统 SHALL 为每次出现位置各保留一条命中项，或合并为一条并记录出现次数；同一请求同一规则同一偏移只保留一条。
7. WHEN 命中项写入, THE 系统 SHALL 保存不超过 120 字的上下文摘录，摘录中保留命中片段。

### Requirement 4: 内置完整开源敏感词库

**User Story:** AS 管理员, I want 产品开箱即带完整开源敏感词库, so that 第一次扫描无需手工导入词表。

#### Acceptance Criteria

1. WHEN 系统首次扫描且本地缓存为空, THE 系统 SHALL 在线下载完整开源敏感词库（konsheng/Sensitive-lexicon）并缓存后作为敏感词检测数据源。
2. WHEN 词库包含分类, THE 系统 SHALL 在命中项上保留原分类名称，供列表筛选使用。
3. WHEN 词库下载或加载失败, THE 系统 SHALL 仍执行 PII 与密钥扫描，并将任务结果标记为部分成功，错误信息写明词库未能加载。
4. WHILE 第一版运行, THE 系统 SHALL 使用已缓存的上游词库进行敏感词匹配；词库条目增删改管理界面留待后续版本。
5. WHEN 管理员在内容审计页请求同步词库, THE 系统 SHALL 重新从上游下载分类词库、覆盖本地缓存并刷新检测自动机。
6. WHEN 内容审计页展示扫描状态, THE 系统 SHALL 显示词库最近一次成功同步或下载的时间。

### Requirement 5: 24 小时循环任务与手动执行

**User Story:** AS 管理员, I want 内容审计作为独立循环任务每 24 小时运行，并允许立即执行, so that 历史数据能被扫完，新数据也能按日补扫。

#### Acceptance Criteria

1. WHEN 应用启动, THE 系统 SHALL 注册循环任务 `content_audit`，默认间隔 86400 秒。
2. WHEN 到达下次执行时间且该任务空闲, THE 系统 SHALL 启动一次增量扫描。
3. WHEN 管理员在定时任务页点击该任务的立即请求, THE 系统 SHALL 在空闲时启动一次增量扫描，行为与到达间隔时相同。
4. WHEN 该任务已在运行, THE 系统 SHALL 拒绝并发执行，并返回与现有定时任务一致的忙碌状态。
5. WHEN 管理员修改该任务的刷新间隔, THE 系统 SHALL 将合法间隔持久化，并按新间隔计算下次执行时间；允许范围与现有循环任务的 `interval_seconds` 一致。
6. WHEN 一次扫描结束, THE 系统 SHALL 在定时任务页展示上次完成时间、成功或失败、处理的请求记录数、新增命中项数、错误信息（若有）。
7. WHEN 扫描覆盖尚未扫描或自上次成功扫描后有更新的请求记录, THE 系统 SHALL 将这些记录标记为已扫描，使后续增量运行跳过无变化记录。

### Requirement 6: 历史全量与增量衔接

**User Story:** AS 管理员, I want 第一次运行扫完全量历史，之后只扫新数据, so that 4000 余条存量记录能被覆盖，日常任务保持可完成。

#### Acceptance Criteria

1. WHEN 内容审计任务首次对某条请求记录运行, THE 系统 SHALL 扫描该记录当时已存在的全部消息。
2. WHEN 已扫描请求记录随后新增消息（会话续写）, THE 系统 SHALL 在下一次增量扫描中只处理新增或变更的消息，并补写对应命中项。
3. WHEN 单次任务达到内部批次上限仍有剩余记录, THE 系统 SHALL 结束本轮并保留进度，使下一轮（定时或手动）从剩余记录继续。
4. WHEN 一轮扫描因进程退出中断, THE 系统 SHALL 在下次启动后从上次进度继续，已写入的命中项保持可用。

### Requirement 7: 任务与页面的可观测性

**User Story:** AS 管理员, I want 在内容审计页看到扫描进度和命中统计, so that 我知道清单是否已经覆盖正式服存量。

#### Acceptance Criteria

1. WHEN 管理员打开内容审计页, THE 系统 SHALL 展示最近一次扫描状态：未运行、运行中、成功、失败、部分成功，以及已扫描请求数 / 总请求数、命中项总数。
2. WHEN 扫描正在运行, THE 系统 SHALL 允许管理员继续浏览已有命中项。
3. WHEN 最近一次扫描失败, THE 系统 SHALL 在内容审计页和定时任务页同时展示失败原因摘要。

### Requirement 8: 权限、保留与安全展示

**User Story:** AS 管理员, I want 命中项仅对已登录管理员可见，并在列表里看到摘录而非完整密钥, so that 审计可用且凭据不会在列表中整段暴露。

#### Acceptance Criteria

1. WHEN 未登录用户访问内容审计页面或命中项 API, THE 系统 SHALL 将其导向登录或返回未授权。
2. WHEN 命中类别为密钥, THE 系统 SHALL 在列表摘录中遮罩密钥中间部分，仅保留可识别的前缀与末尾若干字符。
3. WHEN 命中类别为 PII, THE 系统 SHALL 在列表摘录中对证件号、手机号、银行卡号做部分遮罩。
4. WHEN 管理员打开请求详情查看原文, THE 系统 SHALL 按现有记录详情的权限展示完整消息，并高亮命中片段。

## Out of Scope (第一版)

- 请求/响应实时拦截、脱敏改写、阻断转发
- 越狱 / 提示词注入的语义检测
- LLM-as-judge 自动打分
- 中文人名 NER
- 敏感词库的后台增删改与远程热更新
- 命中项的「已阅 / 误报」工作流（列表先只读）
- 对采样策略的依赖（合规扫描走增量全覆盖，不靠随机抽样）
