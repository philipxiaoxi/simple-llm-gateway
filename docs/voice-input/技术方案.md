## 1. 需求分析

### 1.1 原始需求拆解

用户的原话可以拆成 7 条功能需求 + 3 条非功能需求：

| # | 需求 | 我的理解与补充 |
|---|---|---|
| R1 | 手机端 Web 页面，按住说话、松开发送 | 因为要「边说边出字」，改为**按住即开始流式上传**，松开只发 `finish`。语音数据不再攒到松开才发 |
| R2 | 服务器调用 ASR 把录音转文字 | 改为**阿里云实时 ASR**，服务商先写死 |
| R3 | AI 优化文字表达 | 优化对象是**每个已结束的句子**，不是整段录音（分段优化才能边说边改） |
| R4 | 新建 Node.js 小程序连 WebSocket，把文本填进电脑输入框 | 新建 `voice-desktop/`，含「注入模式」开关 + 全局快捷键，默认关闭以防误注入 |
| R5 | 管理页面提供「房间」按钮，加入房间才能用 | 房间 = 多对多配对单元：1 个房间 = N 个手机 + M 台电脑。含房间码/PIN/一键生成手机链接 |
| R6 | 语音输入房间所有日志必须记录 | 6 类事件全落库：ASR 原文、润色文、下发、回执、失败、耗时 |
| R7 | AI 模型可选本站上游账号与模型 | 房间级配置：账号 + 模型 + 提示词 + 开关，后台可视化选择 |
| N1 | 手机 → 电脑 端到端要快 | 目标：说完一句到上屏 P50 < 1.2s，ASR 首字 < 800ms |
| N2 | 服务商暂时写死 | 代码留 `AsrProvider` 接口，房间表已有 `asr_provider/asr_model` 字段，将来换供应商零改表 |
| N3 | 不能崩、不能丢 | ASR/润色/下发任一步失败都必须降级到「原文照发」并记日志 |

### 1.2 核心用户故事

1. **作为写作者**，我在手机上按住说话，电脑光标所在的输入框（微信/飞书/VSCode/浏览器）立刻开始出字，我松手后 AI 把口语改成书面语，并**原地替换**我刚说的那段，我不需要碰键盘。
2. **作为使用者**，我打开手机页面，输入 6 位房间码，看到「已连接 · 电脑端在线」，才敢开始说话。
3. **作为管理员**，我在后台创建房间、选好润色用的账号和模型、生成二维码给手机扫码，然后在「日志」里回看每一次说话：原文是什么、AI 改成了什么、下发给了哪台电脑、电脑是否确认收到、各环节耗时多少。
4. **作为使用者**，我说到一半发现说错了，只要在手机上点「撤销上句」，电脑端就会把这句从输入框删掉（可选，P1）。

### 1.3 关键场景与边界

| 场景 | 期望行为 |
|---|---|
| 用户按住在安静环境说话 | 实时出字，句子结束后 1s 内润色替换 |
| 用户在嘈杂环境说话 | ASR 出错 → 润色纠正错别字；润色失败 → 保留原文，界面提示 |
| 用户手动敲了键盘 | **立刻放弃**所有未提交的替换，只做追加，避免「改动用户内容」 |
| 电脑端掉线 | 手机端顶部横幅变红「电脑端离线」，文本仍记录，电脑重连后可补发最近 N 条 |
| 手机上滑取消录音 | 松手时丢弃该段（不上屏） |
| 一次说很久（>30s） | 按句子持续出字；单次录音上限 120s，超时自动收尾并提示 |
| 两台电脑加入同一房间 | 广播给所有桌面端（可配置成「仅主设备」） |

### 1.4 明确不做（本期）

- ❌ 不做语音合成回放、不做多语言翻译
- ❌ 不做音频文件长期存储（默认不落盘；如需存，见 §7.5 留了开关）
- ❌ 不做声纹识别 / 说话人分离（Paraformer 8k 版才有情感，本期不用）
- ❌ 不做移动端原生 App（Web 页面 + 添加到主屏幕足够）

### 2.1 为什么这样分层

- **手机不直连阿里云**：Key 绝不能下发到浏览器；同时服务端才能统一记录日志、做润色、做房间广播。
- **桌面端不轮询 HTTP**：文本要「边出边填」，必须是长连接；且上行只有回执，流量极小。
- **润色走本站网关内部调用**：直接调 `call_chat()`，不绕一圈 HTTP，也天然复用账号密钥解密、`header_spoof`、网关代理（agent）等既有能力。
- **单进程 asyncio 直通转发**：后端只在 WS 之间搬字节，不做音频缓冲与转码，延迟可控。

## 3. 【重点】文本替换方案设计

这是整个需求里最容易做砸的地方，单独成章。

### 3.1 问题定义

语音是流式的，ASR 的中间结果会不断被修正（`你好` → `你好我` → `你好我们`），润色又是异步回来的。要在**用户可能正在别的输入框里工作**的前提下，把「已经填进去的文字」改成新版本，必须同时满足：

1. 不能改动用户自己敲的内容
2. 不能因为替换把光标位置搞乱
3. 替换要尽量无感（不闪、不跳、不丢字）
4. 任何时候出错都必须能安全停在「原文已正确上屏」这个状态

### 3.2 设计选型

| 方案 | 说明 | 评价 |
|---|---|---|
| A. 每个 partial 都全量重打 | 每次中间结果都清空重打整段 | ❌ 闪烁严重，长句卡顿，输入法会被打断 |
| B. 只追加、润色结果追加在后 | 原文照打，润色文另起一行 | ❌ 用户要自己删原文，体验不成立 |
| C. 逐字符 keycode 模拟 | 用 CGEvent 逐个字符敲 | ❌ 中文/emoji 需要键盘布局映射，且会触发输入法候选框 |
| D. 剪贴板粘贴 + 段落尾部替换（**采用**） | 用 `pbcopy` + `Cmd+V` 注入；需要改动时用「Shift+← 选中 N 字符」再粘贴新内容 | ✅ 跨 App 通用、中文/emoji 天然支持、每次替换是原子的 |
| E. Accessibility API 直写控件 | 用 AXUIElement 直接 set value | ❌ 大量 Electron/Qt 应用不暴露可写 AX 属性，兼容性差 |

**采用 D**，并叠加三层保护：段落快照、停顿窗口、用户输入让位。

### 3.3 核心模型：Segment（文本段）

后端把一次录音拆成若干 **Segment**，每个 Segment 是替换的最小单位：

```ts
type Segment = {
  segId: string          // 段落唯一 ID（服务端生成，客户端幂等依据）
  seq: number            // 房间内自增序号，客户端用来排序与丢弃乱序
  rev: number            // 版本号：0=ASR 原文(partial)，1=ASR 终稿，2=润色终稿
  text: string           // 该版本的完整文本（**快照，不是 diff**）
  state: 'partial' | 'final' | 'revised' | 'aborted'
  final: boolean         // 是否还会再变（true 表示服务端承诺不再改这段）
  t0: number             // 服务端时间戳(ms)，用于日志与排序
}
```

**关键设计决策 1：永远下发「整段快照」，不下发 diff。**
理由：WS 会重连、会乱序、会重复；快照让客户端可以无状态对齐，diff 一旦丢一帧就永久错位。

**关键设计决策 2：`rev` 是状态档位（0/1/2），不是自增版本号。**
同一段在 `rev=0` 阶段会被反复下发（服务端按 ≥120ms 节流，`text` 持续增长），所以客户端
**不能**用 `(segId, rev)` 去重，也不能「rev 不大于本地就丢」——否则一句话只会出第一帧。
正确做法见 [协议参考.md §2.4](./协议参考.md)。

**关键设计决策 3：`roomBusy` 是「延后替换」而不是「放弃替换」。**
整段录音期间 `roomBusy` 恒为 true；若一见它就放弃，纠错终稿（rev=2）将永远替换不回去。
因此客户端把替换推迟到房间空闲，超时才降级为只追加。

### 3.4 客户端替换算法（`voice-desktop`）

客户端为每个 `segId` 维护一条账：

```ts
type InsertedSegment = {
  segId: string
  text: string        // 当前已注入到输入框的文本（本地认为的）
  chars: number       // text 的 Unicode 字符数（Array.from(text).length）
  committed: boolean  // 是否已「落定」（落定后不再替换，只允许追加）
}
```

收到新快照时的算法：

```
onSegment(snapshot):
  prev = inserted[snapshot.segId]

  # 1) 新段落：直接追加
  if prev == null:
      anchor = 当前段落末尾锚点
      paste(snapshot.text)          # 见 §3.5 锚点协议
      inserted[segId] = { text: snapshot.text, chars: len, committed: false }
      ack(segId, rev, 'inserted')
      return

  # 2) 已经是终稿且不允许再改：只做正向追加（文本变长部分）
  if prev.committed:
      delta = snapshot.text.slice(commonPrefixLen(prev.text, snapshot.text))
      if delta.length > 0: paste(delta)          # 不回改，只补
      prev.text = snapshot.text; ack(...)
      return

  # 3) 常规替换：共同前缀裁剪 → 只重贴「差异尾部」
  p = commonPrefixLen(prev.text, snapshot.text)   # Unicode 字符级
  tailOld = prev.chars - p
  tailNew = snapshot.text.slice(p)
  if tailOld == 0:
      paste(tailNew)                              # 纯追加
  else:
      if tailNew.length == 0:
          backspace(tailOld)                      # 纯回删
      else:
          selectBack(tailOld)                     # Shift+← × k 分批
          paste(tailNew)                          # 选中即被覆盖
  inserted[segId] = { text: snapshot.text, chars: len, committed: snapshot.final }
  ack(segId, rev, 'replaced')
```

**示例**（用户说「你好我们明天见」）：

| 时刻 | 事件 | 输入框内容 | 动作 |
|---|---|---|---|
| t0 | partial `你好` | `你好` | 追加粘贴 |
| t1 | partial `你好我们` | `你好我们` | 共同前缀 `你好`，尾部 `我们` 纯追加 |
| t2 | partial `你好，我们明天` | `你好，我们明天` | 共同前缀 `你好` → 尾部 `，我们明天`，回删 2 字符后重贴（一次原子操作） |
| t3 | final `你好，我们明天见。` | `你好，我们明天见。` | 尾部 `见。` 纯追加，段落锁定为 final |
| t4 | revised `你好，我们明天见。`（润色无改动） | 不变 | 无操作 |
| t5 | revised `你好，我们明天见吧。` | `你好，我们明天见吧。` | 共同前缀 `你好，我们明天见` → 尾部 `吧。`；回删 1 字符 + 粘贴（**原子瞬时，人眼不可辨**） |

### 3.5 锚点协议（怎么保证替换的是「我们注入的那段」）

三种可选实现，按落地难度排序，**推荐 A**：

- **A. 包围哨兵（推荐）**：注入段落时前后加不可见哨兵 `\u2063`（INVISIBLE SEPARATOR）。替换时客户端只信任「上一个 insert 区之后的、自己维护的尾部」，且每次替换前读取当前选区位置，若与期望值不符则降级为「只追加 + 提示用户」。哨兵会出现在最终文本里，需要提供「清除哨兵」按钮（或在段落 final 且润色完成后自动用一次替换去掉尾部哨兵）。**权衡：为了简单，v1 直接不插哨兵，改用实现 B。**
- **B. 位置预期 + 明确边界（v1 采用）**：客户端记住「本次会话注入的总字符数 `expectedPos`」。每次替换前用 `CGEventSource` 读取当前光标位置（macOS：`CGEventCreate(NULL)` + `kCGMouseEventClickState` 不可靠，改用 `AXUIElement` 取 `kAXSelectedTextRangeAttribute`；拿不到就跳过检查），
  - 光标 == `expectedPos` → 允许替换
  - 光标 != `expectedPos` → **放弃替换**，只做追加，并把 `aborted` 事件上报后端记录日志
  - 用户手动移动光标、手动敲字、切换窗口都会自然导致不符 → 自动保护
- **C. 显式插入模式 + 全局热键**：`voice-desktop` 默认不注入，用户按 `⌥⌘V` 进入「插入模式」，模式只对当前前台 App 有效，切窗即退出。**v1 采用 C+B**：模式保证「注入只发生在我想注入的地方」，B 保证「替换只发生在我注入的那段」。

### 3.6 停顿窗口（何时允许替换）

替换必须发生在**用户没在说话、也没在打字**的时刻，否则会和「用户的下一个动作」抢光标。

规则：

```
每次收到 segment 快照（需要回改）时：
  if 用户正在录音（本房间有 active recording）:
      暂存到 pending[segId]，等录音停止或停顿信号
  if 距最后一次 text 更新 < 600ms:              # 打字/上屏仍在进行
      推迟到 600ms 后再执行（最多推迟 3s，超时则放弃）
  if 距最后一次录音活动 < 800ms 且仍未 finish:   # 用户还在说话，句子未完
      推迟
  else:
      立即执行替换
```

后端会把 `room.busy`（是否有手机正在录音）随每条消息下发，客户端无需自己推算。

优先级：**用户输入 > 替换**。任何时候只要检测到用户可能手动输入（`injectedFlag` 脏了、光标不符、焦点窗口变化），立刻把所有 `committed=false` 的段落标记为 `committed=true`（放弃后续替换），并上报 `replace.abandoned` 事件。

### 3.7 上滑取消 / 撤销

- 上滑取消：手机端在 `pointercancel` 或位移 > 60px 时发 `discard`，后端把当前未 finish 的段标 `aborted` 并广播 `segment.abort`，桌面端执行 `backspace(chars)` 撤掉该段。**保护**：只有 `committed=false` 的段才允许 abort。
- 撤销上句（P1）：手机端「撤销」按钮 → 后端 `segment.abort` → 客户端回删。若段落已 committed（用户已接着打字），改为「提示无法撤销」。

### 3.8 输入框兼容性矩阵

| 目标 | 注入方式 | 备注 |
|---|---|---|
| 微信 / 飞书 / QQ | pbcopy + Cmd+V | 正常，不触发输入法候选框 |
| VSCode / Cursor | 同上 | 编辑器需在编辑态（有光标），否则无效果 |
| Chrome / Safari 网页输入框 | 同上 | 正常 |
| iTerm / Terminal | 同上 | 可用，注意 `Cmd+V` 在 vim 模式下变成粘贴寄存器 |
| 全屏游戏 / 无输入焦点 | — | 无法注入，客户端显示「当前无输入焦点」 |

### 3.9 为什么不用 AX API 写入

`AXUIElementSetAttributeValue(kAXValueAttribute)` 在 Electron（VSCode、飞书）和多数 Qt 应用上不可写或写入后不触发 `input` 事件。剪贴板粘贴是这些 App 唯一稳定的通用路径，因此作为主方案。

### 4.3 WebSocket 协议

**统一约定**：控制帧为 JSON 文本帧；音频为二进制帧；所有消息带 `type`；服务端消息带 `ts`（epoch ms）。

#### 端点 1：手机音频上行

```

```

`token` 由 `POST /api/voice/rooms/{room_id}/join` 下发，payload：


这里**刻意不绑定 `sub`/`ver`（管理员版本）**——手机用户不是管理员，没有 Admin 行；签名密钥仍用 `app_secret_key`，验证时只校验 `scope/role/room_id/exp`。桌面端 token 同理（`role: "desktop"`）。

### 4.4 阿里云实时 ASR 接入（`voice_asr.py`）

**已实测确认**（见 [协议参考.md](./协议参考.md)）：

- 端点：`wss://dashscope.aliyuncs.com/api-ws/v1/inference`
- 握手头：`Authorization: Bearer sk-ws-…`（**不加 `X-DashScope-DataInspection`**，官方建议非必要不启用）
- 模型：**默认 `qwen-audio-3.0-asr-flash-streaming`**，备选 `fun-asr-realtime` / `paraformer-realtime-v2`（三者协议完全一致，改模型名即可切换，已实测）
- 音频：单声道 PCM16LE 16kHz，二进制帧直发

#### 4.4.1 实时 ASR 模型选型（实测对比）

> **不要用 `qwen3-asr-flash-realtime`（即"Qwen3-ASR-Flash"的实时版）**。它用的是会话式
> `session.update` / `turn_detection` / `input_audio_buffer.commit` 协议，不走 `run-task`；
> 官方明确其**不返回时间戳**，且"每次会话结束后需主动断开连接，不支持连接复用"。它是为
> 实时语音**对话**（AI 陪聊、语音助手）设计的，不是为听写设计的。详见 §4.4.2。

实测条件：macOS `say -v Tingting` 合成中文语音「你好，我们明天下午三点开会，请提前准备好方案。」→ 16kHz 单声道 PCM，逐 100ms 帧发送。

| 模型 | 协议 | 实测转写 | 中间结果条数 | 单价（华北2·北京） | 字级时间戳 |
|---|---|---|---|---|---|
| **`qwen-audio-3.0-asr-flash-streaming`** | `run-task` ✅ | 你好，我们明天下午3点开会，请提前准备好方案。 | 7 | `0.00033 元/秒` | ✅ |
| `fun-asr-realtime` | `run-task` ✅ | 你好，我们明天下午3点开会，请提前准备好方案。 | 7 | `0.00033 元/秒` | ✅ |
| `paraformer-realtime-v2` | `run-task` ✅ | 你好，我们明天下午三点开会，请提前准备好方案。 | 11 | `0.00024 元/秒` | ✅ |
| ~~`qwen3-asr-flash-realtime`~~ | `session.*` ❌ | 未测（协议不同） | — | `0.00033 元/秒` | ❌ 官方明确不支持 |

三者的文本准确度在同一水平（差异只在数字规范化：Paraformer 的 ITN 输出「三点」，Qwen/Fun-ASR 输出「3点」），选型主要看**成本、出字密度、多语言**：

| 场景 | 推荐 |
|---|---|
| 默认（中文听写，追求效果与体验） | `qwen-audio-3.0-asr-flash-streaming`，与最强模型同价 |
| 想省钱（约为 Qwen 的 73%） | `paraformer-realtime-v2`，中间结果更密，老牌稳定 |
| 中英混说 / 复杂噪声环境 | `fun-asr-realtime`（官方定位就是"中英文自由切换 + 更强噪声鲁棒性"） |
| 8k 电话音频 | `fun-asr-flash-8k-realtime`（`0.00022 元/秒`）或 `paraformer-realtime-8k-v2` |

**成本量级**（`0.00033 元/秒`）：每天说 1 小时 ≈ `1.19 元/天` ≈ `36 元/月`；新账号有 `36,000 秒（10 小时）` 免费额度（北京地域，90 天内有效）。paraformer 另有一个每月 1 日自动发放的 10 小时免费额度。

**我们的做法**：模型名做成房间级配置（`voice_rooms.asr_model`），默认写 `qwen-audio-3.0-asr-flash-streaming`，后台可随时切到 paraformer 观察成本与效果。因为协议完全一致（都在同一个 `wss://dashscope.aliyuncs.com/api-ws/v1/inference` 端点），切换零代码改动——已实测三个模型都能用同一份报文跑通。

#### 4.4.2 为什么不用 `qwen3-asr-flash-realtime`

| 维度 | `run-task` 系（Paraformer / Fun-ASR / Qwen-Audio-3.0-ASR-Flash-Streaming） | `session.*` 系（Qwen3-ASR-Flash-Realtime） |
|---|---|---|
| 断句控制 | `max_sentence_silence`（毫秒阈值，直接可调） | `session.turn_detection.{silence_duration_ms, threshold}` |
| 客户端提交 | 不需要（服务端 VAD 自动断句） | 需要 `input_audio_buffer.commit`（Manual 模式） |
| 时间戳 | 句级 + **字级** | **不支持** |
| 连接复用 | 支持（`finish-task` 后可再 `run-task`） | **不支持**，每次会话后须断开 |
| 定位 | 听写 / 字幕 / 会议记录 | 实时语音对话（AI 陪聊、语音助手） |

对"按住说话 → 边说边出字 → 上屏"来说，时间戳与连接复用都用得上（将来做卡拉 OK 式高亮、或复用连接降延迟），而会话式协议的 `turn` 语义与我们的"一次按住=一个会话"模型是重复的，反而多一层状态机。

#### 4.4.3 ASR 已经"润色"了吗？还需要再接文本大模型吗？

**结论：ASR 只做「忠实转写 + 标点 + 数字规范化」，不做「书面化改写」；但 `disfluency_removal_enabled` 能吃掉很大一块，所以文本模型应该被定位为「纠错层」而不是「文风润色层」。**

实测对比（同一段 13 秒口语：「嗯那个我想说就是我们明天下午三点开会这个事情吧就是说请大家都提前准备好方案然后呃如果有问题的话就提前在群里面讲一下」）：

| 配置 | 输出 |
|---|---|
| Qwen，`disfluency_removal_enabled=false` | `问那个我想说就是我们明天下午3点开会这个事情吧，就是说请大家都提前准备好方案，然后呃如果有问题的话就提前在群里面讲一下。` |
| **Qwen，`=true`** | `我想说，我们明天下午3点开会。请大家都提前准备好方案，如果有问题的话，就提前在群里面讲一下。` |
| Paraformer，`=true` | `问我想说我们明天下午三点开会这个事情把请大家都提前准备好方案，然后如果有问题的话，就提前在群里面讲一下。` |
| Fun-ASR，`=true` | `问那个，我想说就是我们明天下午3点开会这个事情吧，就是说请大家都提前准备好方案，然后呃如果有问题的话就提前在群里面讲一下。` |

三条可验证的事实：

1. **默认配置下 ASR 什么都不删**——「那个 / 就是说 / 呃」原样保留，只加了标点和数字规范化。ASR 的职责是"听清"，不是"写好"。
2. **`disfluency_removal_enabled=true`（本项目该参数按房间可配）能删掉大部分赘词并重组标点**，Qwen 效果最明显（直接变成一句通顺的话）。**这一档应默认开启**，它把"必做"的部分做掉了。
3. **但 ASR 修不了"听不懂"造成的错**：这段里「嗯」被听成「问」，「吧」被听成「把」。`disfluency_removal` 是**删词**策略，无法把错字改成对字——调任何 ASR 参数都改不掉。

**所以文本大模型的边界很清楚：**

| 只有文本大模型能做 | ASR（含去赘词）做不到 |
|---|---|
| 用上下文改同音/近音错字（「问」→「嗯」、「把」→「吧」） | ❌ 删词策略无法改字 |
| 上下文纠专有名词（人名、产品名、领域术语） | ❌ 声学上就听错了 |
| 书面化改写（口语 → 书面语、长句断句） | ❌ 只做标点预测 |
| 去冗余重述（"就是说""这个事情吧"这类句式层面的啰嗦） | ⚠️ 只能删孤立语气词 |
| 按房间调风格（会议纪要 / 邮件 / 代码注释） | ❌ 没有"目标风格"概念 |

**代价那一面**：多一跳文本模型 = 多 700ms~2.5s 延迟 + 每句约 ¥0.0005~0.003 的 token 成本，并且引入「替换出错反而改坏原文」的风险。

**最终决策（写进实现）**：

1. `disfluency_removal_enabled` **默认 `true`**（房间可关）；ASR 侧先把"必做"的干净度拿到手。
2. 文本模型**保留**，但定位为**纠错层**：
   - 提示词重点从"润色表达"改为"**只修错、不改写**"——错别字 / 同音字 / 标点 / 明显赘余，不改变原意、不增删信息；
   - 用规则判断**值不值得替换**：长度变化 > 30%、或与原文字符编辑距离 > 40% 时，判为"过度改写"，**放弃应用**，保留 ASR 原文（防幻觉改坏原文）；
   - 结果与原文完全相同 → 不替换、不广播、记 `polish.skipped`。
3. 后台提供**三档开关**（房间级），让用户用真实语料自己决定这笔账：
   - `off`：只用 ASR（最省、最快）
   - `error_fix`（默认）：只纠错，不改写
   - `rewrite`：允许书面化改写（会议纪要类场景）
4. 后台「用示例文本试润色」按钮**同时展示 ASR 原文与模型输出**，让用户一眼看出这一跳到底有没有价值。

> 如果实测下来你们的语料在 `error_fix` 档几乎没有改动，直接把房间设成 `off` 即可——方案保留了这条退路，不是非接不可。

`run-task` 参数（本项目取值，三个模型通用）：

```json
{
  "header": { "action": "run-task", "task_id": "<uuid>", "streaming": "duplex" },
  "payload": {
    "task_group": "audio", "task": "asr", "function": "recognition",
    "model": "qwen-audio-3.0-asr-flash-streaming",
    "parameters": {
      "format": "pcm",
      "sample_rate": 16000,
      "disfluency_removal_enabled": true,
      "punctuation_prediction_enabled": true,
      "inverse_text_normalization_enabled": true,
      "semantic_punctuation_enabled": false,
      "max_sentence_silence": 700,
      "heartbeat": true,
      "language_hints": ["zh"]
    },
    "input": {}
  }
}
```

> `max_sentence_silence` 默认 1300ms，语音输入场景调到 **700ms** 让句子边界更快出现，润色更早介入。取值范围 [200, 6000]。

**结果解析**：`payload.output.sentence.{text, sentence_end, begin_time, end_time}`；`sentence_end=true` 表示该句终稿。`payload.usage.duration` 是计费时长（秒），写入 `voice_sessions.asr_usage_seconds`。`header.event` 另外可能是 `task-finished` / `task-failed`（后者带 `error_code`/`error_message`，连接不可复用）。

**连接生命周期**：一次录音会话一条连接（不做连接池，避免多路复用状态机复杂度）。官方支持连接复用（`finish-task` 后可再 `run-task`），P2 优化再考虑，可省 100ms 左右建连时间。

**核心接口**：

```python
class VoiceAsrSession:
    async def start(self) -> None: ...
    async def push_audio(self, pcm: bytes) -> None: ...
    async def finish(self) -> AsrResult: ...      # 发 finish-task，等 task-finished
    async def abort(self) -> None: ...
```

回调：`on_partial(text)`、`on_final(text, begin_ms, end_ms)`、`on_error(code, message)`。
超时保护：建连 10s、`task-started` 15s、`task-finished` 15s，超时按 `AsrError` 处理并降级。

### 4.5 润色调用链（`voice_polish.py`）

**复用本站已有能力，不新增 HTTP 调用**：

```python
from app.services.bridge import call_chat, prepare_credential
from app.services.credentials import require_upstream_credential

async def polish_text(db, *, account_id: int, model: str | None,
                      text: str, context: list[str], system_prompt: str | None,
                      temperature: float = 0.2, timeout: float = 12.0) -> PolishResult:
    account = db.get(UpstreamAccount, account_id)          # 校验存在 + 可用
    if account is None or not is_account_available(account):   # key_models.is_account_available
        return PolishResult.skipped("账号不存在或不可用")
    model = (model or "").strip() or first_model_id(account.models_json)
    credential = require_upstream_credential(account)       # 自动解密 / agent 代理账号
    messages = [
        {"role": "system", "content": system_prompt or DEFAULT_POLISH_PROMPT},
        {"role": "user", "content": build_user_prompt(text, context)},
    ]
    try:
        result = await asyncio.wait_for(
            call_chat(account, messages, model, False,
                      {"max_tokens": 512, "temperature": temperature}, credential),
            timeout=timeout,
        )
        return PolishResult.ok(clean(result.choices[0].message.content), model)
    except Exception as exc:
        return PolishResult.failed(str(exc))                # 失败绝不抛给主流程
```

**默认提示词**（按 `polish_mode` 二选一，房间可覆盖）：

`error_fix` 档（**默认**，纠错层——前提是 ASR 的 `disfluency_removal_enabled=true` 已经把语气词删干净了）：

```
你是语音识别的纠错器，不是改写器。输入是一句语音识别结果。
只做下面四件事：
1. 改正同音字、近音字、明显错别字（例如「问」应为「嗯」、「把」应为「吧」）；
2. 结合上下文改正听错的专有名词（人名、产品名、专业术语）；
3. 修正标点与断句；
4. 删除残留的口语赘词与无意义重复。
严格禁止：
- 不改变原意，不增加原文没有的信息，不删减有效信息；
- 不改变句式、不书面化、不调整语气、不做同义替换；
- 保留专业术语、代码、URL、数字原样；
- 直接输出结果，不要解释、不要加引号、不要 Markdown；
- 如果原文没有明显错误，原样输出。
```

`rewrite` 档（会议纪要类场景）：在上述基础上允许把口语重组为书面语、合并冗余表述，但仍要求不改原意、不增信息。

**过度改写保护（重要）**：模型有幻觉风险，一次「自作聪明」的替换会直接改坏用户的内容。因此应用前做两道校验：

```python
def should_apply(raw: str, polished: str) -> tuple[bool, str]:
    if not polished:                                   return False, "empty"
    if polished == raw:                                return False, "no_change"   # 记 polish.skipped
    if abs(len(polished) - len(raw)) / max(len(raw), 1) > 0.30:
        return False, "too_long"                       # 长度变化 > 30%：判为过度改写
    if edit_distance_ratio(raw, polished) > 0.40:
        return False, "too_different"                  # 编辑距离 > 40%：判为改写而非纠错
    return True, "ok"
```

被判定为过度改写时 → **保留 ASR 原文**，记 `polish.result`（`applied=false`、`reason`），手机端与日志页都能看到"模型想改成什么、为什么没采用"。`rewrite` 档把阈值放宽到 0.6。

**上下文**：把该会话已定稿的前 1–2 句作为 `context` 一起给出（各截断 200 字），保证人称、术语一致。

**兜底策略（重要）**：润色失败/超时/返回空/被判过度改写 → `polish_status=failed|skipped`，**不替换**，段落保持 ASR 原文（`rev=1`），手机端显示「未润色」角标，日志记 `polish.failed`。用户拿到的一定是可用文本。

**计费可见性**：调用后可选写一条 `request_logs`（`protocol="voice_polish"`、`account_id=润色账号`、`api_key_id=None`），这样润色消耗能出现在现有的「概览 / 记录审计」里。**建议开启**，方便观察成本。

### 4.6 会话编排（`voice_session.py`）

```
handle_binary(pcm):
    session.audio_bytes += len(pcm); session.audio_ms += len(pcm)/32   # 16k*2B
    await asr.push_audio(pcm)                       # 直通，不做任何缓冲/转码
    hub.touch(room)                                 # 刷新 busy 计时

on_asr_partial(text):
    seg = session.current_segment
    seg.rev = 0; seg.text = text
    hub.broadcast_snapshot(seg, final=False)        # 本地节流：≥120ms 才下发一次
    hub.broadcast_to_phone(asr.partial)

on_asr_final(text, begin, end):
    seg.rev = 1; seg.state = 'final'; seg.raw_text = text
    persist(seg)                                    # 段落入库（原文先落库，防丢）
    hub.broadcast_snapshot(seg, final=True)
    hub.broadcast_to_phone(asr.final)
    log_event('asr.final', text=text)
    session.next_segment()                          # 开新段落
    if room.polish_mode != 'off': spawn(polish_and_revise(seg))   # 不阻塞音频路径

async polish_and_revise(seg):
    res = await polish_text(..., mode=room.polish_mode)
    if not res.ok:
        log_event('polish.failed', error=res.error); return       # 保留 ASR 原文
    apply, reason = should_apply(seg.raw_text, res.text)          # 过度改写保护，见 §4.5
    if not apply:
        log_event('polish.result', input=seg.raw_text, output=res.text,
                  applied=False, reason=reason); return            # 不改、不广播
    if seg.state == 'aborted': return               # 已被撤销
    # 竞态保护：润色回来时，若该段之后已经有 ≥2 段新内容，或距终稿 > 12s，则放弃替换
    if session.segments_after(seg) >= 2 or now - seg.finalized_at > 12_000:
        log_event('polish.result', payload={'applied': False, 'reason': 'stale'}); return
    seg.rev = 2; seg.state = 'revised'; seg.polished_text = res.text
    hub.broadcast_snapshot(seg, final=True)
    hub.broadcast_to_phone(segment.revised)
    log_event('polish.result', input=seg.raw_text, output=res.text, ms=res.ms, applied=True)
```

**并发与背压**：
- 单房间同时只允许 1 个 `active` 录音会话；新 `start` 会先 `finish` 旧会话。
- 润色并发上限（全局）默认 4，用 `asyncio.Semaphore` 控制，避免打爆上游。
- 手机上行音频如果积压（`websocket.client_state` 或自维护队列 > 5s 音频），丢弃最旧帧并上报 `backpressure` 事件。

### 4.7 广播注册表（`voice_hub.py`）

对标 `services/local_agent_relay.py` 的写法：

```python
@dataclass
class VoiceConnection:
    room_id: str
    role: str                      # phone | desktop
    client_uid: str
    websocket: WebSocket
    send_lock: asyncio.Lock = field(default_factory=asyncio.Lock)
    async def send_json(self, payload): ...
    async def send_bytes(self, payload): ...

class VoiceHub:
    _rooms: dict[str, dict[str, VoiceConnection]]
    def register(...) / async def unregister(...)
    async def broadcast_snapshot(self, room_id, seg, final) -> int
    async def broadcast_to_phone(self, room_id, payload) -> None
    def room_state(self, room_id) -> dict          # busy / desktops / phones
voice_hub = VoiceHub()
```

- 每个连接一把 `send_lock`，避免并发 `send_json` 交错（这是 `local_agent_relay` 已经踩过的坑）。
- 广播失败（连接已断）只记 warning 并跳过，不影响其他接收方。
- 所有 DB 写入一律 `await asyncio.to_thread(...)`，绝不阻塞事件循环（音频路径尤其敏感）。

### 5.2 手机端录音页（核心）

**视觉**：整屏深色，顶部状态条（房间名 / 连接状态 / 电脑端在线数），中部实时字幕区（大字、自动滚动），底部一个巨大的圆形「按住说话」按钮（`≥ 96px`，`touch-action: none`，`user-select: none`）。

**采集链路**：

```
getUserMedia({audio:{channelCount:1, echoCancellation:true, noiseSuppression:true,
                     autoGainControl:true, sampleRate:48000}})
  → AudioContext
  → AudioWorkletNode('pcm-capture')     # 128 帧/块，约 2.67ms
  → 累积到 100ms
  → Float32 → Int16（带软限幅）
  → 48k → 16k 线性插值重采样
  → ws.send(ArrayBuffer)                # 二进制帧
```

- **AudioWorklet 兜底**：Safari < 14.5 / 非安全上下文不支持时，降级为 `ScriptProcessorNode`（已废弃但可用），代码里做能力探测。
- **重采样**：48k→16k 用 3:1 线性插值即可（语音够用，成本极低）。若设备原生就是 16k（少见），跳过。
- **iOS 关键点**：
  1. `AudioContext` 必须在用户手势（`pointerdown`）里 `resume()`；
  2. `getUserMedia` 必须在**安全上下文**（HTTPS 或 `localhost`）——**这是部署硬要求**；
  3. 首次必须由用户手势触发权限弹窗，所以「按住说话」第一次按下时先走一遍权限申请，成功后自动开始本次录音；
  4. 锁屏/切后台会挂起 AudioContext → 监听 `visibilitychange`，回前台提示重按。
- **交互细节**：
  - `pointerdown` → 开始；`pointerup` → `stop`；`pointercancel` / 上滑 > 60px → `discard`
  - 用 Pointer Events + `setPointerCapture`，避免手指滑出按钮后丢事件
  - 录音中按钮扩散脉冲动画 + 顶部计时；超过 `max_recording_seconds` 自动 `stop`
  - 松手后到 `session.done` 之间显示「正在收尾…」，此时不允许开始下一段（避免竞态）

**实时字幕区**：
- 未定稿部分用浅色（`text-mist`）+ 闪烁光标，定稿后转正常色
- 润色返回时，该句**原地淡入替换**（`opacity` 过渡 200ms），并显示小角标「AI 优化」
- 每句右下角显示 `polishMs`，便于用户感知
- 底部两个按钮：「复制全部」「清空」

**回执与状态**：手机端不直接和电脑通信，电脑端回执由服务端广播 `segment.ack` 给手机端 → 手机端在对应句子旁显示 ✓（已上屏）。

### 5.3 桌面客户端（`voice-desktop/`）

详见 [桌面客户端.md](./桌面客户端.md)。要点：

- Node 20+，依赖 `ws`（唯一运行时依赖）+ 可选 `node-notifier`；**不引入原生模块**（避免 rebuild）
- 注入用系统命令：macOS `pbcopy` + `osascript -e 'tell application "System Events" to keystroke "v" using command down'`；先做 `pbcopy`，再做 Cmd+V
- 「Shift+← 选中 N 字符」用 `osascript` 循环 `key code 123 using shift down`（`key code 123` = 左箭头），分批 ≤ 20 次/批
- 全局快捷键 `⌥⌘V` 切换「插入模式」（`osascript` 做不了全局热键，用 Node 侧 `readline` 命令 + 托盘菜单；P2 再上 `node-global-key-listener`）
- 配置 `~/.llm-gateway-voice.json`：`{ "serverUrl", "roomId", "token", "clientUid", "name", "insertMode": false, "clipboardRestore": true }`
- 状态输出：连接状态、当前房间、插入模式、最近注入文本、回执计数、错误
- 断线指数退避重连 + 重连后接收 `recentSegments` 补发

## 7. 日志、可观测性与隐私

### 7.1 一条完整链路的日志样貌

用户在房间里说「你好我们明天见」并润色成「你好，我们明天见。」：

```
10:00:01.120 room.join      phone  小飞的 iPhone 加入
10:00:02.900 session.start  采样率 16000 / pcm_s16le
10:00:04.210 asr.final      seq=1 raw="你好，我们明天见。"
10:00:04.215 segment.send   seq=1 rev=1 → 1 台电脑
10:00:04.268 segment.ack    seq=1 rev=1 ok=true pos=9
10:00:04.220 polish.request account=3 model=deepseek-chat
10:00:04.960 polish.result  in="你好，我们明天见。" out="你好，我们明天见。" ms=740
10:00:04.965 segment.send   seq=1 rev=2 → 1 台电脑
10:00:05.012 segment.ack    seq=1 rev=2 ok=true action=replaced
10:00:05.100 session.finish audio_ms=2100 usage=3s sentences=1
```

### 7.2 指标（可直接加进现有 Dashboard）

- 端到端延迟：`session.stop` → 最后一条 `segment.ack`（P50/P95）
- ASR 首字延迟：`session.start` → 首个 `asr.partial`
- 润色成功率、P50/P95 耗时
- 注入成功率、放弃替换率（按原因分布）
- 每房间每分钟句数、ASR 计费秒数、润色 token 数

### 7.3 数据保留

- `voice_events` 与 `voice_segments` 默认保留 30 天（`VOICE_EVENT_RETENTION_DAYS`）。
  已实现为独立常驻任务 `services/voice_retention.py`：启动 2 分钟后首次执行，之后每 24 小时一次，
  分批 2000 行删除以避免长时间占用 SQLite 写锁；只清理孤儿会话，仍被段落引用的会话保留。
  另提供 `GET /api/admin/voice/storage`（查看规模）与 `POST /api/admin/voice/cleanup`（手动触发）
- 提供「清空本房间日志」按钮

### 7.4 隐私

- 音频默认**不落盘**（`VOICE_STORE_AUDIO=false`）
- 文本日志仅在管理员可见的页面，且房间有 PIN 时手机上不显示历史
- 建议房间页面加提示：「本房间的语音文本会被记录，用于查看与排查」

### 7.5 安全

| 项 | 措施 |
|---|---|
| 阿里云 Key | 只存在服务端 `.env`，绝不下发；`_sanitize` 所有日志输出 |
| 手机令牌 | 房间作用域 JWT，12h 过期，`scope=voice`，无法访问管理接口 |
| 房间 PIN | bcrypt 存储 + 按 IP 限流 + 失败计数 |
| 桌面令牌 | 共享令牌 `VOICE_DESKTOP_TOKEN`（对标 `LOCAL_AGENT_TOKEN`），可轮换 |
| 路径遍历 | WS 路径 `room_id` 正则 `^[a-z0-9]{8}$` 校验 |
| 越权 | 每帧校验 `room_id` 与令牌内 `room_id` 一致 |
| 反向代理 | 必须转发 `Upgrade`/`Connection` 头，否则 WS 握手失败（现有 `/agent/connect` 已有同样要求） |

| 指标 | 目标 |
|---|---|
| ASR 首字延迟（手机→屏幕） | < 800ms |
| 句子终稿 → 电脑上屏 | < 400ms（同城网络） |
| 润色返回 → 替换完成 | < 2.5s（P95，取决于上游模型） |
| 单房间并发 | 4 手机 + 4 电脑 |
| 全局并发录音会话 | 20（可调，注意 DashScope 限流） |
| 单帧开销 | 100ms 音频 = 3200B；1 分钟 ≈ 1.9MB 上行 |
| 语音包月流量估算 | 每天 1 小时 ≈ 115MB |

**容量注意**：DashScope 实时 ASR 有并发与 QPS 限制（按账号），建议在 `voice_hub` 里加全局并发信号量并记录 `asr.rejected` 事件。
